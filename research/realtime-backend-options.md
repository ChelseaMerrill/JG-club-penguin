# Research: Realtime Multiplayer Backend Options

Resolves issue #3 ("Research: realtime multiplayer backend options"). Primary-source research only — official docs, pricing pages, and GitHub repos, no secondary blog summaries.

Domain vocabulary used throughout: **Player**, **Penguin**, **World**, **Room**, **Session**, **Presence** (per-Room, not global), **NPC**, **Interaction**, **Minigame**.

## Recommendation

**Use Supabase Realtime (Channels: Presence + Broadcast) paired with Supabase Auth for Google SSO.**

Supabase Realtime requires no long-lived server process to manage — Presence, Broadcast, and Postgres Changes all run against Supabase's managed infrastructure, so the team never has to solve Render's idle-sleep problem, Fly.io/Railway's now-paid-only hosting, or AWS ops in a 3-day window ([Realtime docs](https://supabase.com/docs/guides/realtime)). Its free tier — 200 concurrent connections, 256 KB broadcast payloads, and native presence primitives ([Realtime limits](https://supabase.com/docs/guides/realtime/limits)) — comfortably covers a hackathon demo. Realtime's **Channel** primitive is a near-exact match for the Room/Presence requirement: subscribing to `supabase.channel('room_01')` gives every client an isolated presence-and-broadcast scope for that Room out of the box, with zero custom room-management code ([Presence docs](https://supabase.com/docs/guides/realtime/presence)). Crucially, Supabase Auth ships Google OAuth as a first-party, same-project integration ([Sign in with Google](https://supabase.com/docs/guides/auth/social-login/auth-google)), and because Auth, Realtime, and a real Postgres database live in one platform behind one client library, the team gets Player identity, relational World/Room/NPC/Interaction data modeling, and per-Room Presence from a single SDK and a single free project. This is a stronger pairing synergy than Firebase (whose free Realtime Database tier supports only 100 simultaneous connections, and whose presence pattern doesn't natively extend to Firestore — where most teams would otherwise store structured Player/Room/NPC data — requiring a Cloud Functions bridge, [Firestore presence solution](https://firebase.google.com/docs/firestore/solutions/presence)) or Colyseus (the best-in-class purpose-built game-room framework, but one that requires hosting a long-lived Node process; free hosts like Render sleep idle WebSocket connections after 15 minutes ([Render free tier docs](https://render.com/docs/free)) and Fly.io/Railway no longer offer meaningful free always-on compute, pushing teams toward Colyseus Cloud's $15/mo plan ([Colyseus pricing](https://colyseus.io/pricing/)) during crunch time). For a 4-person all-web-stack team with zero game-networking experience, the fastest path to a working per-Room-Presence multiplayer demo is the platform that eliminates server-hosting and auth-wiring as separate engineering problems.

**Runner-up: Firebase Realtime Database + Firebase Auth**, on the same "same-platform Auth + Realtime" logic, is the strongest fallback if the team prefers Firebase's simpler JSON-tree mental model or its onDisconnect() presence pattern over Supabase's channel-presence API. See per-candidate detail below.

**If the team wants an actual authoritative game server** (server-side game loop, anti-cheat, more complex Minigame state machines) and is willing to accept $15/mo hosting instead of a free tier, **Colyseus** is the strongest fit for room/state-sync ergonomics and should be reconsidered if Minigames turn out to need server-authoritative logic beyond what a client-driven Presence/Broadcast model comfortably supports.

## Per-Candidate Detail

### Colyseus (colyseus.io)

- **What it is**: A Node.js/TypeScript framework purpose-built for authoritative multiplayer game servers, organized around **Rooms** as the core unit of isolated game state and connected clients.
- **Free tier**: The open-source server is free and self-hostable with "no restrictions" ([pricing](https://colyseus.io/pricing/)). The managed **Colyseus Cloud** offering has no free tier — it starts at $15/month, billed upfront per compute plan, and advertises "no CCU/DAU/MAU limits" and "unlimited bandwidth" at that price ([Colyseus Cloud pricing](https://colyseus.io/pricing/)).
- **Hosting**: Requires a long-lived Node process (the room server keeps in-memory/schema-synced state). Because Fly.io ended its free tier for new orgs in October 2024, and Railway's free trial reverts to a paid Hobby plan, and Render's free tier sleeps after 15 minutes of no inbound traffic — which closes open WebSocket connections without warning ([Render free tier](https://render.com/docs/free)) — there is no reliable always-on free host for a Colyseus server in 2026. Colyseus Cloud ($15/mo) or a small always-on paid VM are the practical options; this is the one candidate that most directly pushes toward paid infrastructure to be reliable during a demo.
- **Learning curve**: Quickstart is a single scaffolding command (`npm create colyseus-app@latest ./my-server`) with presets for minimal/realtime-action/turn-based games, and TypeScript is the primary, best-documented language ([Getting Started](https://docs.colyseus.io/getting-started/)). However, the team must learn Colyseus-specific concepts (Room lifecycle, Schema state sync, client-side room joining) that don't map onto anything they already know from web dev.
- **Auth pairing**: `@colyseus/auth` supports OAuth 2.0 with 200+ providers including Google, plus JWT session handling, but it is a toolkit, not a hosted identity platform — the team supplies `AUTH_SALT`/`JWT_SECRET` and wires up their own user persistence ([Auth Module docs](https://docs.colyseus.io/auth/module)).
- **Per-Room Presence**: Native and central to the framework — a Room *is* the presence/state scope; Colyseus also ships a separate Presence module for pub/sub across multiple server processes when horizontally scaled.

### PartyKit (partykit.io / docs.partykit.io) — now part of Cloudflare

- **Current status**: Cloudflare announced it acquired PartyKit in April 2024 ([Cloudflare blog](https://blog.cloudflare.com/cloudflare-acquires-partykit/); [PartyKit blog](https://blog.partykit.io/posts/partykit-is-joining-cloudflare/)). The original `partykit/partykit` GitHub repository now carries the banner **"Current development of this project is in cloudflare/partykit,"** directing users to the Cloudflare-maintained fork/successor. The standalone `docs.partykit.io` site is not deprecated outright but shows no meaningful recent updates (last substantive update ~March 2025 based on the page's own timestamp).
- **What it is now, technically**: Each PartyKit "Party" (room) is backed 1:1 by a Cloudflare Durable Object, and PartyKit is essentially an opinionated developer-experience layer over Durable Objects + the `workerd` runtime ([How PartyKit works](https://docs.partykit.io/how-partykit-works/)).
- **Free tier / billing**: Deploying to your own Cloudflare account incurs no separate PartyKit platform fee — you pay Cloudflare directly for the Durable Objects/Workers usage ([Deploy to your own Cloudflare account](https://docs.partykit.io/guides/deploy-to-cloudflare/)). Cloudflare's Workers Free plan includes Durable Objects (SQLite-backed) with 400K GB-seconds and 1M requests/month at no cost ([Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)).
- **Hosting simplicity**: Best-in-class — no server process to run or keep awake; it's serverless Durable Objects under the hood.
- **Learning curve**: Rooms are ID-routed ("connecting with the same `id` always reaches the same room instance"), which is a simple mental model, but the product's own migration-in-progress status (docs pointing to a different, actively-developed repo) adds real risk of stale docs or breaking changes during a 3-day build — this is the main strike against it versus its technical merits.
- **Auth pairing**: No first-party identity platform; Google SSO must be wired up independently (e.g., via Auth.js) and a token passed to the Party on connect.
- **Per-Room Presence**: Native via the room/Party-ID routing itself — connections sharing an `id` are implicitly scoped together; there's no dedicated "Presence" API documented distinct from room membership.

### Supabase Realtime (supabase.com/docs/guides/realtime)

- **What it is**: A managed realtime layer over Postgres offering three primitives — **Broadcast** (low-latency ephemeral messages), **Presence** (synchronized per-client state), and **Postgres Changes** (DB change streaming) — all scoped to named **Channels** ([Realtime overview](https://supabase.com/docs/guides/realtime)).
- **Free tier**: 200 peak concurrent connections, 256 KB max broadcast payload, 100 channels per connection, 20 presence messages/sec, 100 messages/sec ceiling ([Realtime limits](https://supabase.com/docs/guides/realtime/limits)).
- **Hosting**: None needed — fully managed by Supabase; the team's game server logic can live entirely client-side or in lightweight Supabase Edge Functions if needed.
- **Learning curve**: Low for web developers — `supabase-js` is a single client covering Auth, Postgres, and Realtime with a consistent async API; the channel/subscribe model resembles pub/sub patterns many web developers already know.
- **Auth pairing**: First-party and same-project — Supabase Auth's Google provider requires only a Google OAuth Client ID/Secret pasted into the Supabase dashboard and a `supabase.auth.signInWithOAuth({ provider: 'google' })` call ([Sign in with Google](https://supabase.com/docs/guides/auth/social-login/auth-google)). Realtime channels can also be secured with Supabase's Row Level Security tied to the authenticated user.
- **Per-Room Presence**: Native and explicit — `supabase.channel('room_01')` isolates Presence state to that topic; per the docs, "a client will receive state from any other client that is subscribed to the same topic," which is exactly the per-Room (not global) scoping this project requires ([Presence docs](https://supabase.com/docs/guides/realtime/presence)).

### Firebase Realtime Database / Firestore (firebase.google.com/docs)

- **What it is**: Two related but distinct managed databases. Realtime Database (RTD) is a JSON tree with native low-latency sync and connection-state primitives; Firestore is a document database with richer querying but no native disconnect-detection.
- **Free tier (Spark plan)**: RTD — 100 simultaneous connections, 1 GB stored, 10 GB/month downloaded; Firestore — 1 GiB stored, 50K reads/day, 20K writes/day, 10 GiB/month network egress ([Firebase pricing](https://firebase.google.com/pricing)).
- **Hosting**: None needed — fully managed, accessed directly from client SDKs.
- **Presence pattern**: RTD has a documented, purpose-built presence idiom using the `.info/connected` special path plus `onDisconnect()`, which "occur[s] whether the client disconnects cleanly or not" ([Offline capabilities / presence](https://firebase.google.com/docs/database/web/offline-capabilities)). Firestore has **no** native equivalent — Firebase's own docs state "Cloud Firestore doesn't natively support presence" and recommend bridging via RTD + Cloud Functions to sync presence into Firestore ([Build presence in Cloud Firestore](https://firebase.google.com/docs/firestore/solutions/presence)). This matters for this project because most teams reaching for "Firebase" today default to Firestore for structured app data (Player/Room/NPC records), which would then require running two Firebase products plus Cloud Functions just to get Presence — RTD alone, used for both structured data and presence, avoids that split but is a less natural fit for relational-ish World/Room/NPC/Interaction data.
- **Learning curve**: Very low — Firebase has the largest tutorial/StackOverflow footprint of any candidate here, and the onDisconnect pattern is copy-paste-able from official docs.
- **Auth pairing**: First-party and same-project — Firebase Auth's `GoogleAuthProvider` with `signInWithPopup`/`signInWithRedirect` is a few lines of code, enabled from the same Firebase console as the database ([Google Sign-In for web](https://firebase.google.com/docs/auth/web/google-signin)).
- **Per-Room Presence**: Achieved via path-based scoping — store presence under a Room-scoped path (e.g., `/rooms/{roomId}/presence/{uid}`) and attach listeners/`onDisconnect()` handlers at that path; clients only subscribe to their current Room's path, giving natural per-Room isolation without a dedicated "channel" concept.

### Custom Socket.io or ws Node server

- **What it is**: A hand-rolled Node.js WebSocket server, most commonly built on Socket.io for its built-in room/namespace abstractions and reconnection handling.
- **Free tier**: The library itself is free (OSS); the constraint is entirely on hosting (see below).
- **Hosting**: Requires a long-lived Node process, same constraint as Colyseus. Render's free tier sleeps after 15 idle minutes, closing open sockets ([Render free tier](https://render.com/docs/free)); Fly.io ended its free tier for new orgs in October 2024; Railway's free trial reverts to a minimal $1/month credit under its paid Hobby plan. Scaling beyond one instance additionally requires the Socket.io Redis Adapter, since "in a multi-server setup, the rooms and sids objects are not shared between the Socket.io servers" ([Rooms docs](https://socket.io/docs/v4/rooms/)).
- **Learning curve**: Highest of all candidates for this team — every layer (protocol, rooms, reconnection/state resync, hosting, scaling, auth) must be built and debugged from scratch in three days, with no managed platform absorbing any of that risk.
- **Auth pairing**: None built in. Google SSO requires either hand-rolling OAuth (e.g., Passport.js + `passport-google-oauth20`) or verifying a token issued by an external provider (Supabase Auth or Firebase Auth) inside the Socket.io connection handshake — extra integration work regardless of choice.
- **Per-Room Presence**: Native and simple once built — `socket.join("room")` plus `io.to("room").emit(...)` scopes both membership and messaging to a Room-sized subset of clients, with automatic room cleanup on disconnect ([Rooms docs](https://socket.io/docs/v4/rooms/)).

### Other candidates considered and ruled out

- **Ably**: Free tier is generous — 6M messages/month, 200 concurrent connections, 200 concurrent channels ([Ably vs Pusher](https://ably.com/compare/ably-vs-pusher)) — and supports Presence channels, but it is a generic pub/sub messaging platform with no bundled identity provider and no game-room/state-sync framework; adopting it would mean redoing the same auth-wiring and room-management work as the custom Socket.io path without that path's flexibility. Not pursued further given time constraints.
- **Pusher**: Similar profile to Ably but a smaller free tier (Sandbox: 200 concurrent connections, 200K messages/day across 100 channels). Same reasoning as Ably — ruled out, not pursued in depth.
- **Nakama / other self-hosted game backends**: Require standing up and operating your own backend infrastructure (typically Docker/Kubernetes), which reintroduces the exact hosting/ops burden this team is trying to avoid in three days, with no first-party free managed tier suitable for a hackathon. Not evaluated in depth given the explicit preference to avoid AWS-style infra work.

## Pairing Synergy Callout

- **Strongest synergy — Supabase Auth + Supabase Realtime**: Both live in the same Supabase project, share the same API keys and JS client (`supabase-js`), and Realtime Channels can be protected using the same auth session used for Google sign-in. This collapses "set up Google SSO" and "set up per-Room Presence" into one platform with one quickstart, which is the single biggest time-saver available for this team's three-day window. ([Realtime](https://supabase.com/docs/guides/realtime), [Auth Google](https://supabase.com/docs/guides/auth/social-login/auth-google))
- **Close second synergy — Firebase Auth + Firebase Realtime Database**: Equally first-party and same-project, with arguably even lower learning friction due to Firebase's enormous tutorial base and the well-known `onDisconnect()` presence idiom. Loses ground only because Firestore (the product most people mean by "Firebase" for structured data today) doesn't share RTD's presence capability, and RTD's Spark free tier caps out at 100 simultaneous connections versus Supabase's 200. ([RTD presence](https://firebase.google.com/docs/database/web/offline-capabilities), [Auth Google](https://firebase.google.com/docs/auth/web/google-signin), [Firestore lacks presence](https://firebase.google.com/docs/firestore/solutions/presence))
- **Notable anti-synergy — Colyseus + hosting**: Colyseus's room/state-sync model is the best technical fit for a "real" game server, but it has no synergistic free hosting partner in 2026 — Fly.io's free tier is gone, Render's free tier actively breaks long-lived WebSocket connections via idle sleep, and Railway has no meaningful permanent free plan. The practical consequence is that adopting Colyseus for this hackathon effectively means adopting Colyseus Cloud ($15/mo) as a package deal, which is a cost/ops tradeoff the team should make consciously rather than by default.
- **Notable anti-synergy — PartyKit's mid-migration status**: Although technically elegant (Durable-Object-backed rooms, no server to run), the standalone PartyKit product is in an acknowledged transition into Cloudflare's own tooling, with its own GitHub repo pointing developers to `cloudflare/partykit` for current development. For a fixed 3-day build, depending on a product mid-migration carries doc-staleness and breaking-change risk that outweighs its hosting-simplicity advantage.
